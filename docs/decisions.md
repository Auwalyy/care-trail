# CARETRAIL — Ambiguities, Decisions and Risks

## Ambiguities resolved (safe defaults — change by configuration, not code)

| # | Ambiguity | Decision |
|---|---|---|
| A1 | "Issuing facility **or** community" | `origin: {type: community \| facility}`; CHW referrals default to their community. |
| A2 | Who sets referral **priority** | Optional; only roles with `referral:set-priority` (facility workers / facility admins) may set it. CHWs cannot, because priority is a clinical judgement. |
| A3 | "Approved referral instructions" | Admin-managed instruction templates that need a recorded clinical approval before use. **Starts empty**: CARETRAIL ships no clinical instructions. |
| A4 | Antenatal/postnatal/immunisation **schedules** | Configurable schedule templates, empty by default. No WHO/NPHCDA schedule is hard-coded; the programme's clinical lead must supply it. |
| A5 | Escalation procedure | Configurable escalation contacts per programme or facility; escalation only records and notifies. |
| A6 | CHW referral authorisation | Per-CHW flag `canIssueReferrals` that a programme admin sets. |
| A7 | Offline login | Online first login is required. After that the app unlocks with a local PIN against the cached session, within a configurable offline grace period (default 14 days). |
| A8 | Patient ID format | Server-generated `CT-P-NNNNNN` per organisation. Offline patients show "Pending ID". |
| A9 | Referral code | `CT-XXXX-XXXX` in Crockford base32 with a check character. Generated only by the server. |
| A10 | Real-time (Socket.IO) | Not needed for the MVP. Facility queues poll every 30 s. Can be revisited. |
| A11 | Retention periods | The fields exist, but values need a programme/legal decision under the NDPA. Default: no automatic deletion. |
| A12 | SMS/voice provider | Provider interface plus `LogOnlyProvider`. No credentials are fabricated, and nothing is marked delivered without a provider. |
| A13 | CHW web access | CHWs use mobile. The web only exposes their profile. |
| A14 | Pilot figures (2/2/10/200/12 weeks) | Stored in `settings` as *targets*. Dashboards show actual vs. target. These are not confirmed deployments. |
| A15 | Patient sign-in | None in the MVP, as specified. |
| A16 | Delivering activation and reset links without an email/SMS provider | Admins create users and get a **one-time activation link** to hand over in person or over a trusted channel. Admins never set passwords. Self-service "forgot password" issues a link but doesn't deliver it until a provider is configured, and it is recorded as `delivered: false`. Only in development is the link written to the log. |
| A17 | Refresh-token reuse on flaky networks | A rotated token used again within 30 s counts as a retry after a lost response: the earlier successor is revoked and a new one issued. After 30 s it counts as reuse, so the family is revoked and audited. The web client serialises refreshes across tabs with the Web Locks API. |
| A18 | Who creates whom | `MANAGEABLE_ROLES`: platform admin → programme/facility/CHW. Programme admin → facility admin, facility worker and CHW, all in their own org. Facility admin → facility workers in their own facility. Platform admins only come from the `create-admin` script. Nobody can edit their own account through `/users`. |
| A19 | Reference data before Phase 3 | Read-only scoped `GET /organisations`, `/facilities` and `/communities` exist now, so users can be linked to them. `npm run seed:dev` creates clearly labelled DEMO data for local use and refuses to run in production. |
| A21 | Pilot targets default | Unset (`null`) until an administrator saves them. The proposed values (2 communities, 2 facilities, 10 CHWs, 200 patients, 12 weeks) can be filled in with one click on the settings page, but are never assumed. |
| A22 | Deactivating reference data in use | Refused with 409 and a count: organisations with user accounts, facilities with staff, communities with CHWs. People must be reassigned first, so nobody is silently left without a valid assignment. Hard deletion isn't offered. |
| A23 | Combining scope filters | Repositories must combine an id filter with a scope filter using `withinScope()` (`$and`), never object spread. Phase 3 tests found that `{ _id: id, ...scope }` let a scope keyed on `_id` replace the requested id. A programme admin requesting another organisation got their own back (200 instead of 404), and the user and CHW repositories had the same latent pattern. Fixed everywhere and covered by `scope-isolation.test.ts`. |
| A24 | Registration minimum | Name, sex, date of birth **or** estimated age, community, care pathway and its key date, plus consent to care coordination. Phone and household are optional. No clinical data is collected. |
| A25 | Duplicate detection | Same organisation and community, same `nameKey` (word order ignored), birth year within ±1. The API warns and never blocks. Overrides are flagged (`possibleDuplicateOf`) and listed for review. Candidates show code, name, birth year and CHW only, never phone or full DOB. |
| A26 | Consent | Append-only, one record per conversation stating every purpose, with the programme's wording version (set in Programme settings). Withdrawing care coordination makes the record `inactive` but keeps it. Withdrawing SMS or voice resets the reminder channel. |
| A27 | Who sees which patients | Platform admins see all, programme admins their organisation, and CHWs only their assigned caseload. Facility staff see none until a referral or appointment links a patient to their facility (Phase 5). Every profile read is audited, so the profile page doesn't refetch on window focus. |
| A28 | Not in Phase 4 | Linking a newborn to the mother is supported by the API (`pathwayDetails.motherPatientId`) but not yet by the web form; it comes with the mobile wizard in Phase 7. Visits are also deferred to Phase 7. |
| A29 | What facility staff see | Through the referral only: name, code, sex, age, care pathway and its key date, reason, instructions and the issuing CHW. No phone, household, consent history or other referrals. Their patient endpoint scope stays "none". |
| A30 | Referral receipt | Shows code, facility and address, dates, CHW, patient name and code, and the approved instructions. It omits the referral reason, because the paper leaves the health system. |
| A31 | Referral gates | A referral needs the patient's facility-sharing consent, an active patient, `canIssueReferrals` for CHWs, an active facility in the same organisation, and approved templates only. Priority can only be set by facility staff. The server is authoritative for status. |
| A32 | Overdue referrals | In Phase 5 they are flagged (`overdue`, an "awaiting arrival" filter and a dashboard count) but don't change state. The `expired` transition and the follow-up task it creates come with Phase 6's missed-care job, so all automatic follow-up lives in one place. |
| A33 | Missed-care scheduling | It runs in the API process every `MISSED_CARE_INTERVAL_MINUTES` (default 15; 0 disables) instead of BullMQ/Redis. Every write is conditional and open tasks are unique per source and reason (`openKey`), so concurrent runs on several replicas are harmless. It uses the server clock only. Redis/BullMQ remains an option if job volume grows. |
| A34 | Automatic follow-up rules | **Appointments**: a scheduled appointment past date + `appointmentOverdueGraceDays` becomes `missed` and gets a task. **Referrals**: one still `issued` after `expectedArrivalBy` becomes `expired` (system event) and gets a task; `follow_up_required` gets a task carrying the facility note. Tasks are due 2 days after creation, belong to the patient's current CHW (and move with reassignment), and are never created for inactive patients. They resolve automatically when the patient attends, the appointment is rescheduled or cancelled, the referral patient arrives, or the facility completes it. |
| A35 | Escalation | Escalation goes to the CHW's supervisor, else all active programme admins of the organisation. It records the notes and recipients and gives them visibility of the task; it makes no clinical decision. In-app notification of recipients arrives with Phase 9. |
| A36 | Pull cursor | The pull cursor is a server timestamp (`updatedAt`) minus a 5-second overlap, not the monotonic `syncSeq` planned in Phase 0. Every synced collection already has an indexed `updatedAt`; a global sequence counter would be a write hotspot. The overlap re-sends a few records, which is harmless (upsert by id). Deletions are not needed because records are never hard-deleted; leaving the caseload is handled by `assignedPatientIds`. |
| A37 | Sync reuses the online services | `/sync/push` calls the same service methods as the REST endpoints, so validation, scope, consent, audit and duplicate rules cannot drift between online and offline. The ledger (`sync_operations`) stores each op's final answer, so a replay returns it unchanged. |
| A38 | Hausa wording | The Hausa interface text in `apps/mobile/utils/i18n.ts` is a **draft** written without a native-speaker review. It must be reviewed by Hausa-speaking CHWs or programme staff before the pilot. Clinical text (instruction templates) is never machine-translated: `bodyHa` is entered and approved by the programme. |
| A39 | What the phone does offline | Register patients, record visits, book appointments, create referrals (no code until synced; the receipt says so), record follow-up attempts and resolve tasks, update contact details. Identity changes, status changes, reassignment, consent changes after registration, cancelling referrals and recording attendance need the web app or a connection. These have more serious conflict consequences and are rare for CHWs. |
| A40 | Offline sign-in | Online sign-in first, then a 4–6 digit PIN (salted, iterated SHA-256 in SecureStore) unlocks offline within `offlineSessionGraceDays` of the last online contact. 5 wrong PINs clear the session and require an online sign-in. The app locks after 5 minutes in the background because phones are often shared. Sign-out wipes the encrypted database and its key. |
| A41 | Education content and reminder wording | CARETRAIL ships no health content and no approved reminder wording. Education items go draft → in review → approved → published; changing the text or audio of reviewed content returns it to draft and removes it from phones. Programme admins author and publish (`education:manage`); recording the clinical approval stays with platform admins (`education:approve`), kept from Phase 0 as a separation of duties. The built-in SMS templates contain only facility, date and referral code; their Hausa is a draft. Day-before reminders are **off** until the programme switches them on in settings. |
| A42 | Notification delivery | One record per message; text is rendered from a template at send time (never free text, never stored phone numbers). Consent and phone are checked when queued **and** when sent. Providers: `none` (default, recorded as "not sent: no provider") and `log` (development only, refused in production). No real SMS/voice gateway is integrated: that needs a contract, sender-ID registration and credentials (implement `NotificationProvider`). Push is not built (no device tokens yet). Transient failures retry 5 times with backoff from 1 minute; claims are atomic so several API replicas can dispatch. In-app messages go to staff for new follow-up tasks and escalations. |
| A43 | Audio storage | `ObjectStorage` with a local-disk driver (default; back up the folder) and an S3 driver (credentials from the standard AWS chain, server-side encryption). Uploads are checked by type, size (10 MB) and file signature, stored under server-generated keys, and served only to signed-in users through the API. The S3 driver has not been tested against a real bucket. The mobile app shows text only; audio plays in the web app. |
| A44 | Reports | Six fixed reports (monthly trend, referrals by facility, appointments by facility, communities, health-worker activity, follow-up outcomes) with period, community and facility filters, as JSON or CSV. Rows are facilities, communities, staff, reasons or months, never patients. Rates exclude cases that cannot count (cancelled referrals; appointments not yet recorded) and totals recompute rates rather than averaging them. Platform admins must pick an organisation; facility admins get only the facility reports, always for their own facility; CHWs have no access. Grouping runs in the API over projected fields, adequate for pilot volumes; move it to MongoDB `$group` pipelines if volumes grow. **Small numbers are not suppressed**: reports are for programme staff, not publication. Anyone publishing them should suppress small cells first. |
| A45 | CSV exports | UTF-8 with BOM and CRLF so Excel shows Hausa names correctly; cells starting with `= + - @` are prefixed with `'` to block formula injection; every download is audited (`analytics.export`: report, period, row count). |
| A20 | Web UI translation and the top-bar search/notification centre | Deferred. The Hausa/English i18n layer is built with the mobile app in Phase 7 and then applied to the web. Global search and notifications come with Phases 4 and 9, so no non-functional controls are shown before then. |

## Critical technical risks

| Risk | Impact | Mitigation |
|---|---|---|
| MongoDB transactions need a replica set | Referral transitions and sync must be atomic | docker-compose runs a single-node replica set. Tests use `MongoMemoryReplSet`. Startup checks fail fast if transactions are unsupported. |
| Sync correctness (duplicates, lost writes, restarts) | Patient safety and data integrity | Idempotency ledger, `clientId` unique indexes, local transactional outbox, cursor saved with data, dependency ordering, tests for replay and crash. |
| SQLCipher on low-end Android | Performance/compatibility | Benchmark on a 2 GB RAM device in Phase 8. Keep the working set small (assigned patients only). |
| NativeWind 4 ↔ Tailwind 3 pin in a Tailwind 4 monorepo | Build breakage | Mobile declares its own `tailwindcss@3.4`. npm nests it. Verify `expo export`. |
| TypeScript 7 native port | Tool incompatibility | Pinned to TS 6.0. |
| Device clocks are wrong | Wrong ordering, false overdue | Server time is authoritative for status and overdue logic. Client time is stored separately as `clientRecordedAt`. |
| SMS cost and delivery in Nigeria (DND lists, sender ID registration) | Reminders not delivered | Provider abstraction, delivery receipts, consent checks, voice fallback. Sender ID registration is an operational task. |
| NDPA compliance | Legal | DPIA, NDPC registration and a DPO are organisational tasks. The platform provides consent, audit, minimisation, retention hooks and export/erasure tooling. |
| Clinical safety of content | Harm | Approval workflow is enforced in code. Unapproved content cannot be distributed. |
| Low digital literacy | Adoption | Large targets, icons + text, Hausa, a 6-step wizard with drafts, and usability testing with CHWs. |
